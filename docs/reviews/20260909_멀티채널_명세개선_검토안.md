# O.S.M.U 2단계 확장을 위한 명세 개선 검토안

작성일: 2026-09-09. 상태: 검토안. 기존 MODULE_SPEC v23과 워크플로우 v19를 대체하거나 변경하지 않는다.

## 입력과 근거

- 사용자 목표: 1단계 티스토리 파일럿에서 2단계 티스토리·워드프레스·네이버 블로그로 확대. 이후 쇼츠/릴스 중 추가 채널 고려.
- 기준: MODULE_SPEC_20260522_v23.md, 워크플로우_시각화_20260522_v19.html.
- 참고: BUGI, 「Codex로 네이버 블로그 다계정 자동화하기」, 2026-09-07. https://x.com/Bugi952/status/2096926625225187364
- 원문은 브라우저에서 확인했다. 저자의 운영 경험은 설계 참고이며 우리 환경에서 검증된 결과가 아니다. 플랫폼별 최신 기능·정책과 실제 연결 가능성은 별도 검증한다.

## 아티클에서 가져올 원칙

계정마다 운영 기준과 로그인 환경을 분리하고, 근거 자료와 현재 작업 상태를 보존한다. 승인된 본문·이미지·배치·발행 설정을 버전으로 고정한다. 편집기 입력 이후 화면을 검사하고, 발행 요청 이후 플랫폼 결과를 다시 읽어 성공 여부를 판단한다. 결과가 모호하면 재발행 대신 확인을 우선한다.

위는 참고 글의 요약이다. 아래 데이터 모델·모듈 경계·우선순위는 O.S.M.U에 대한 제안이다. 저자의 특정 모델 조합, 동시 작업 수, 계정 수, 발행 상한은 그대로 채택하지 않는다.

## 가장 중요한 경계: 하나의 주제와 여러 발행본

키워드는 시작 입력이다. 여러 채널이 재사용할 중심 산출물은 주제·독자 질문·주장·검증된 근거를 담은 공통 자료 묶음으로 둔다. 동일 HTML을 모든 플랫폼으로 보내는 구조로 고정하지 않는다.

- source_input: 현재는 keyword만 지원. 향후 URL·문서 등은 입력 타입 확장 지점만 확보.
- topic / source_packet: 주제, 핵심 질문, facts, 출처, 확인일, 적용 기간, 불확실성, 재사용 가능한 자산.
- content_variant: 공통 자료를 대상 채널·블로그 독자에 맞춰 구성한 발행본.
- publication: 발행본이 어느 계정·블로그에 언제 어떤 상태로 전달됐는지 기록.

한 주제가 세 블로그에서 발행되면 공통 자료 1개와 대상별 발행 기록 3개가 생긴다. 서로 다른 독자·각도는 필요한 만큼 variant를 나눈다. 일부 플랫폼 실패가 이미 성공한 다른 발행을 되돌리지 않는다.

## 모듈별 재사용 경계

| 모듈 | 공통 기능 | 채널·플랫폼별 기능 또는 추가 조사 |
|---|---|---|
| keyword_researcher | 후보 관리, 평가 기록, 중복·재평가, 주제 선정 | 수요 신호, 검색/추천 노출 특성, 가중치, 하드컷. 네이버 검색량은 모든 채널의 인기도 지표가 아님 |
| collector | 출처 수집 기반, 사실 정규화, freshness, 근거 추적, 부족 시 중단 | 경쟁 콘텐츠 검색·분석, 글 구조/영상 구조 탐색, 주제별 공신력 소스 |
| contents_maker | 검증된 자료 입력, 주장-근거 연결, 자산 관리, 버전 관리 | 블로그 구조와 영상 대본, 플랫폼 표현·길이·이미지 배치 |
| checker | 사실·출처·누락·버전 확인, 승인 처리 | HTML 구조, 편집기 렌더링, 영상 자막·길이·음성 등 |
| publisher | 작업 상태, 승인 확인, 중복 방지, 재시도 판단, 결과 재확인 | 인증, 편집기 조작/API, 미디어 전달, 예약, 원격 상태 읽기 |
| 메시징 | 이벤트→메시지, 글별 메시지 연결, 업데이트, 액션 기록 | Slack 전송/수정/상호작용 구현. 향후 다른 알림 채널 어댑터 |
| 계정·풀 | 공유 키워드 사전과 평가 이력 | 운영 대상별 후보 가시성·선정·잠금·사용 이력·주제·페르소나 |

모듈마다 별도 서버를 만들 필요는 없다. 한 프로젝트·한 DB 안에서 인터페이스와 책임을 분리한다.

## MODULE_SPEC 변경 체크리스트

### 0장: 범위와 용어

- [ ] 이번 릴리스 목표를 블로그 3개 플랫폼으로 명시. 영상은 이번 구현 범위에서 제외.
- [ ] channel(블로그/숏폼), platform(티스토리/워드프레스/네이버), account(인증 계정), destination(실제 블로그) 구분.
- [ ] source_input → topic/source_packet → variant → publication 관계 명시.
- [ ] 공통 자료 승인과 대상별 발행본 승인을 분리.

### 1장: keyword_researcher

- [ ] 현재 검색 점수는 검색 기반 블로그용 프로필로 한정. 플랫폼 점수로 보이게 이름 붙이지 않음.
- [ ] 평가에 signal_provider, channel/profile, model_version, evaluated_at 보존.
- [ ] 키워드 전체 보관소와 대상별 풀·사용 이력 분리. 한 블로그의 사용이 다른 플랫폼 발행까지 잠그지 않도록 범위 명시.
- [ ] 의도적인 동일 source 재활용과 동일 destination 내 중복 발행 구분.
- [ ] 500 검색량·블로그 30개 등 현재 하드컷을 영상까지 공통 적용하지 않음.

### 2장: collector

- [ ] 공통 자료 수집과 채널별 경쟁 콘텐츠·구성 분석의 산출물을 구분.
- [ ] fact에 출처 URL, checked_at, 적용 시점, 근거 문장/위치, 불확실성 추가 검토.
- [ ] 이미 수집한 동일 자료 재사용과 만료 자료 재확인 기준 명시.
- [ ] 특정 플랫폼의 H2 패턴을 공통 source의 필수 구조로 고정하지 않음.
- [ ] 자료 부족 시 중단 원칙 유지. 채널별 구성 변경은 필요한 부분만 재생성.

### 3장: contents_maker

- [ ] HTML 이전에 제목·문단·소제목·이미지·캡션·링크를 표현하는 간단한 블록 구조 도입.
- [ ] 블록 id를 이미지 배치 기준으로 사용. 최종 변환은 플랫폼별로 담당.
- [ ] destination별 독자·톤·자료 기준·참고 예시 설정. 참고 글의 형식과 최신 사실을 분리.
- [ ] 같은 source에서 같은 글을 복제할지, 독자·각도를 바꿀지 편집 정책 명시.
- [ ] 본문·이미지·순서·제목·태그·대상·예약 설정을 묶는 revision 정의.

### 4장: checker

- [ ] 공통 검사 + 채널 규칙 + 플랫폼 입력 후 화면 검사 분리.
- [ ] 승인 기록을 revision 및 destination에 연결. 승인 후 내용 변경은 새 revision 및 재검토.
- [ ] source 동일성을 의도적 재활용으로 인식하되 원문 복제와 무근거 주장은 계속 검사.
- [ ] 블로그의 PC·모바일 표현, 이미지 순서, 링크, 누락을 최종 편집기에서 확인.
- [ ] 사용자 수정이 어떤 검사·승인을 무효화하는지 정의.

### 5장: publisher

- [ ] 공통 prepare / verify / publish-or-schedule / readback 계약 정의.
- [ ] 세 플랫폼별 지원표: 인증, 초안 저장, 미디어, 서식, 예약, 발행, 수정, 결과 읽기.
- [ ] 승인본 임의 변경 금지. 편집기에서 문제가 생기면 새 revision으로 돌아감.
- [ ] 인증 만료·계정 불일치·대상 불확실 시 중단 및 재연결 흐름.
- [ ] 발행 요청 결과가 모호하면 confirmation_pending 상태. 결과를 읽기 전 재시도 금지.
- [ ] destination + revision + 발행 의도 기준 중복 방지. 원격 post_id/URL과 검증 시각 저장.
- [ ] 예약됨과 발행됨을 구분. 세 대상의 부분 성공 허용 및 실패 대상만 재처리.
- [ ] 현재 랜덤 시간·대기 시간은 보편적인 플랫폼 정책이 아니라 프로젝트 운영 설정으로 명명.

### 6장: 공통 데이터·운영

- [ ] accounts의 cookie_path 고정 가정을 제거하고 인증 수단별 연결 참조로 확장.
- [ ] destination_profile, source_packet, content_variant/revision, publication, approval, event 관계 정의. 초기에는 일부를 JSON으로 묶어도 됨.
- [ ] 기존 contents.status 하나로 세 플랫폼 전체 상태를 표시하지 않음.
- [ ] Slack은 DB 상태를 보여주는 창으로 사용. 메시지 자체를 작업 상태의 원본으로 사용하지 않음.
- [ ] message_ts, channel_id, publication/revision 연결을 저장해 같은 메시지 업데이트.
- [ ] 오래된 Slack 버튼·중복 액션은 현재 revision/state 확인 후 처리.
- [ ] 실행 시 명세 버전·입력 버전·결과·오류·비용 기록. 역할별 작업 이력도 같은 기준 버전을 사용.

## 워크플로우 변경안

키워드 → 주제 후보 평가 → 대상 블로그 선택 → 공통 자료/주장 구성 → 구조·자료 검토
→ 대상별 구성·제작 → 대상별 내용 검사·승인본 고정 → 플랫폼 편집기/API 전달
→ 실제 표현 확인 → 허용된 예약/발행 → 원격 결과 재확인.

메시징과 상태 기록은 전 과정에 붙인다. 실패는 공통 자료 실패와 대상별 제작·발행 실패로 구분한다.

## 빠르게 결과를 내기 위한 구현 순서

1. 세 플랫폼에서 고정된 샘플 글 한 편의 초안 저장·재열기·형식 보존부터 검증. 게시 기능 검증은 승인된 테스트 범위에서만 수행. 로그인과 편집기 제약을 먼저 알아야 생성기를 잘못 만들지 않는다.
2. 결과에 맞춰 공통 블록 형식, 대상 정보, revision, publication 상태와 완료 조건 확정.
3. 자료 묶음 하나에서 세 플랫폼 발행본을 생성하고 검수하는 최소 흐름 구현.
4. 대상별 결과 확인까지 연결한 뒤 키워드 자동 선정·풀 고도화·예약 일괄 처리 추가.
5. 영상은 나중에 channel 생성기·검사 규칙·publisher를 추가. 현 단계에서 영상 전용 시스템이나 범용 플러그인 프레임워크를 만들지 않음.

첫 통합 완료 조건: 동일 source_packet에서 세 대상 발행본을 생성, 대상별 승인 revision과 실제 저장/발행 결과를 대조하고, 한 대상 실패 시 나머지 결과를 유지한다. 초안 검증 완료와 공개 발행 완료는 별도로 기록한다.

## 추가 확인과 미결

- WordPress.com인지 자체 호스팅 WordPress인지, 각 대상 블로그와 인증 방식 확인.
- 각 플랫폼의 현재 지원 API/편집기/정책은 공식 문서와 실제 계정에서 검증. 참고 아티클만으로 확정하지 않는다.
- 실제 deadline과 처음 필요한 산출물이 공개 발행인지 승인 가능한 초안인지 확인.
- 기본 제안은 같은 근거를 재사용하되 독자·각도·표현을 대상에 맞게 조정. 다중 플랫폼이라는 이유만으로 별도 키워드 점수를 강제로 만들지 않는다.
- 기존 코드 재사용/재작성은 위 계약을 확정한 다음 판단. 명세가 바뀐 상태에서 이전 일탈 전체를 먼저 고치지 않는다.
- 기존 두 지침 내부의 불일치도 확정 전에 정리: MODULE_SPEC 8장의 ‘상위 블로그 부족 fallback 미결’은 상세 절의 확정 내용과 불일치. 워크플로우 config 표의 LLM 단독 fallback 설명도 후반 중단 규칙과 불일치. 1-A ‘LLM 분석 없음’은 수평·수직 청크 분해의 LLM 호출과 책임 경계를 명확히 적는다.
