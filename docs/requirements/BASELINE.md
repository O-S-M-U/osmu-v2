## 충돌과 변경 처리 규칙

- `docs/baseline/`의 기준 사본은 읽기 전용이며 직접 수정하지 않는다.
- 승인된 변경은 새 버전의 명세 또는 워크플로우 파일로 만들고, 변경 근거와 승인 내용을 `docs/decisions/`에 남긴다.
- 새 버전이 승인되기 전까지 위 표의 경로와 SHA-256 조합을 동일 revision의 기준선으로 사용한다.
- 기준선 확인, 코드 존재, 로컬 검증, 외부 서비스 검증, 공개 발행 완료는 서로 다른 상태로 기록한다.

### 버전 변경·결정 절차

1. **변경 제안 등록**: 기준 문서와의 충돌, 모호성 또는 변경 필요성을 발견한 작업자는 관련 작업을 `decision_required`로 바꾸고 작업 ID, 영향받는 요구사항 ID, 현재 기준선의 경로·버전·SHA-256, 제안 내용과 대안을 기록한다. 구현자는 이 단계에서 어느 해석도 임의로 선택하지 않는다.
2. **제안본 생성**: 변경 내용은 `docs/baseline/`의 사본을 덮어쓰지 않고 새 버전 파일로 작성한다. 파일명과 문서 본문에 이전 버전보다 높은 버전, 작성일, 이전 기준선, 변경 요약을 표시한다. 승인 전 파일에는 `proposal` 상태를 명시하며 기준 문서로 인용하지 않는다.
3. **결정 기록 연결**: `docs/decisions/YYYYMMDD-<topic>.md`에 결정 대상, 선택지, 영향 범위, 승인자, 승인 시각, 승인된 파일 경로·버전·SHA-256을 남긴다. 기존 결정 기록은 수정하지 않고 후속 결정이 이전 결정을 대체하면 양쪽 경로를 새 기록에서 연결한다.
4. **승인 게이트**: 사용자 승인과 결정 기록이 모두 확인되기 전에는 제안본을 승인된 기준 문서로 표시하거나 구현·검사의 기준으로 사용하지 않는다. 반려 또는 미결인 제안은 `proposal` 또는 `decision_required` 상태를 유지한다.
5. **새 기준선 검증**: 승인된 새 문서의 바이트 크기와 SHA-256을 계산하고, 결정 기록에 적힌 값 및 문서 버전과 일치하는지 확인한다. 명세와 워크플로우를 함께 바꾸는 경우 두 파일의 조합을 하나의 기준선 revision으로 검증한다.
6. **기준선 교체**: 검증이 통과하면 이 문서의 기준 파일 표에 새 경로·버전·날짜·크기·SHA-256, 승인 결정 경로, 적용 Git revision을 기록한다. 작업 보드와 추적표가 새 기준선 revision을 가리키도록 갱신한 뒤 후속 작업을 재개한다.
7. **이전 기준선 보존**: 교체된 기준 파일과 그 해시·적용 기간·대체 결정 경로는 삭제하거나 수정하지 않는다. 이 문서의 기준선 이력에 남겨 과거 구현과 증거가 사용한 기준을 재현할 수 있게 한다.

승인된 새 기준선은 `사용자 승인 결정 기록 + 불변 문서 경로 + 문서 버전 + SHA-256 + 적용 Git revision`의 조합으로 식별한다. 이 다섯 항목 중 하나라도 없거나 서로 일치하지 않으면 기준선 교체는 완료되지 않은 것으로 판정한다.

### 0.2 — MODULE_SPEC 전 요구사항 원자화

- 시작 조건: `0.1B`가 검토를 통과해 상위 작업 `0.1`의 의존성이 해소된 뒤 시작한다.
- 원문 시작 위치: 고정 해시의 `docs/baseline/MODULE_SPEC_20260522_v23.md`에서 `## 0. 개요 (Overview)`(현재 파일 10행)부터 문서 순서대로 읽는다.
- 기록 시작 위치: `docs/requirements/TRACEABILITY.md`의 `## 추적표` 아래 예시 행을 첫 실제 Requirement ID 행으로 교체한다.
- 추출 범위: 제목 요약이 아니라 입력, 출력, 내부 로직, DB 갱신 시점, 오류·fallback, 정책 게이트, 오픈 이슈를 포함해 `## 9. 변경 이력 (Changelog)`까지 전수 확인한다. 원문 충돌이나 모호성은 원자화 과정에서 결정하지 않고 `decision_required`로 기록한다.
