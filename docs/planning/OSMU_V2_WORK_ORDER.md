## 모델 배치 원칙

- GPT-5.6 Luna: 대량의 짧고 반복적인 분류·서식 정리에만 사용한다. 요구사항 의미 판정이나 완료 판정에는 단독 사용하지 않는다.
- GPT-5.6 Terra: 문서 추출, 상태 기록, 보고서 초안, 단순 회귀 수정처럼 일상적이고 경계가 분명한 작업에 사용한다.
- GPT-5.6 Sol: 기능 구현, 외부 플랫폼 검증, 조사 결과 종합처럼 정확성과 처리량을 함께 요구하는 기본 작업 모델이다.
- GPT-6 Astra: 명세 충돌, 아키텍처, 실패 복구, 보안, 최종 요구사항 적합성처럼 누락 비용이 큰 판정에 사용한다.
- 기본 effort는 Medium이다. 단순 반복은 Low, 설계·충돌·원격 실패·최종 감사는 High를 사용한다. 높은 effort는 사용량을 늘리며 항상 더 좋은 결과를 보장하지 않으므로 일괄 적용하지 않는다.

## 두 사람의 병렬 작업 방식

1. 모든 작업은 위 ID를 사용하고 한 명의 주 담당자를 둔다. 같은 요구사항을 동시에 고칠 때는 작업을 더 작은 ID로 나눈다.
2. 각 담당자는 별도 브랜치 또는 worktree에서 작업하고, 시작 시 `in_progress`, 검토 요청 시 `review`, 증거 확인 후 `verified`로 바꾼다.
3. 완료 보고에는 작업 ID, 관련 요구사항 ID, commit/PR, 실행한 검사, 증거 경로 또는 원격 URL, 남은 위험을 포함한다.
4. 자기 보고만으로 `done`이 되지 않는다. 명세 연결, 변경 결과, 검사 결과, 증거가 모두 있어야 한다.
5. 한 채널의 실패는 다른 채널의 성공을 되돌리지 않는다. 불명확한 원격 결과는 재시도 전에 조회한다.

## 중간관리자 에이전트

중간관리자는 코드를 대신 작성하는 세 번째 개발자가 아니라, 저장소의 증거를 읽어 두 작업 시간축을 하나로 맞추는 조정·감사 에이전트다. 이름은 `OSMU Coordinator`를 사용한다.

### 입력

- 확정 MODULE_SPEC·워크플로우와 요구사항 추적표
- 작업 ID별 담당자·상태·의존성·예상치
- 두 사람의 commit/PR, 검사 결과, 외부 검증 증거
- 결정 기록과 변경 요청

### 매 실행 시 하는 일

1. 기준 문서 revision과 작업자가 사용한 revision이 같은지 확인한다.
2. 각 작업의 자기 보고와 commit·검사·증거를 대조한다.
3. 같은 파일·요구사항의 병렬 충돌, 막힌 의존성, 오래 갱신되지 않은 상태를 찾는다.
4. 요구사항 추적표에서 구현·검사·증거가 비어 있는 항목을 표시한다.
5. 통과한 작업만 `verified`로 올리고, 다음에 병렬로 시작할 수 있는 작업을 제안한다.
6. 범위·명세 변경은 자동 확정하지 않고 `decision_required`로 올린다.

### 권한과 모델

- 기본 권한은 읽기 및 상태 보고다. 코드 병합, 명세 변경, 외부 발행, Slack 전송은 담당자 승인이나 이미 합의된 자동화 규칙이 있어야 한다.
- 정기 상태 동기화: GPT-5.6 Terra, Medium.
- 충돌·요구사항 누락·완료 판정: GPT-6 Astra, Medium.
- 릴리스 전 MODULE_SPEC 전수 감사: GPT-6 Astra, High.

### 상태 규칙

`planned → in_progress → review → verified → done`을 기본으로 하고 `blocked`, `decision_required`를 보조 상태로 둔다. `done`은 관련 요구사항이 모두 `verified`이고 병합된 결과가 기준 브랜치에서 다시 검사된 뒤에만 허용한다.

### 저장소에 둘 관리 파일

```text
docs/spec/MODULE_SPEC_V2.md
docs/spec/WORKFLOW_V2.md
docs/requirements/TRACEABILITY.md
project/TASK_BOARD.yaml
docs/progress/<담당자>/<YYYYMMDD>.md
evidence/<작업-ID>/
docs/coordination/STATUS.md
docs/decisions/<YYYYMMDD>-<주제>.md
```

중간관리자 에이전트 자체 기억은 기준 자료가 아니다. 위 파일과 Git 이력이 유일한 공유 기록이며, 에이전트는 매번 이를 읽어 상태 보고서를 재생성한다.

## 사용량 운영 규칙

구독 사용량은 하루 고정 토큰 한도가 아니다. 작업 시작 전 Codex의 Settings → Usage에서 5시간 창과 주간 잔량을 확인하고, 각 할당은 아래 순서로 닫는다.

1. 산출물과 진행 위치를 저장한다.
2. 추적표와 작업 상태를 갱신한다.
3. 검사 증거와 미결 항목을 기록한다.
4. 다음 할당이 단독으로 시작될 수 있도록 정확한 시작점을 남긴다.

이 규칙을 지키면 사용량 창이 끝나도 완료되지 않은 작업을 같은 문맥에 의존하지 않고 이어갈 수 있다.
