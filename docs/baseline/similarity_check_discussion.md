# 유사도 검증 시스템 설계 논의

> 작성자가 쓴 글과 참고 소스 간의 유사도를 판별하는 시스템 설계에 관한 논의 정리

---

## 📐 시스템 구조 개요

### 검증 2단계 구조

| 단계 | 방식 | 기준 |
|------|------|------|
| 1단계 | 문장 단위 임베딩 → 크로스 체크 | 문장 최대 유사도 **35% 이하** |
| 2단계 | 전체 글 임베딩 → 유사도 체크 | 전체 유사도 **15% 이하** |

---

## 🔗 문장 수정 → 전체 유사도 변화 관계

### 원리
전체 글 임베딩은 개별 문장들의 의미를 종합해서 벡터로 표현한다.  
따라서 **특정 문장 수정 → 전체 임베딩 벡터 변화 → 참고 소스와의 코사인 유사도 변화**로 이어진다.

### 변화 정도에 영향을 주는 요소
- 수정한 문장이 글 전체에서 차지하는 **비중**이 클수록 효과 큼
- **의미까지 바꾼 수정**인지, **표현만 바꾼 수정**인지에 따라 차이 있음
- 문장이 짧거나 비중이 작으면 전체 유사도 변화폭은 작을 수 있음

### 실용적 흐름
```
문장 단위 유사도 검사
    ↓
35% 초과 문장 식별 → 사용자 수정
    ↓
수정된 글 전체 재임베딩
    ↓
전체 유사도 재계산 → 15% 이하 확인
```

## 🎨 실시간 수정 가이드 UX 설계

### UX 관점
- "뭘 어떻게 고쳐야 하지?" 막막함 해소
- 유사도 수치만 보여주는 것보다 **행동 가능한 피드백** 제공
- Grammarly, Word 맞춤법 검사와 유사한 익숙한 패턴

### 구현 방식별 난이도

| 방법 | 내용 | 난이도 |
|------|------|--------|
| **LLM 기반 대안 문장 추천** | 유사도 높은 문장을 API에 넘겨 2~3개 대안 제시 | ★★☆ |
| **실시간 유사도 변화 표시** | 수정 중 유사도 수치가 실시간으로 변하는 모습 표시 (debounce 처리 필요) | ★★★ |
| **단어/어미 단위 하이라이트** | 어떤 단어가 문제인지 토큰 수준으로 표시 (한국어 형태소 분석 필요) | ★★★★ |

### 추천 구현 조합
> **LLM 대안 추천 + 간소화된 실시간 피드백**

```
유사도 높은 문장 감지
    ↓
LLM이 대안 문장 2~3개 제시
    ↓
사용자가 선택하거나 직접 수정
    ↓
저장 시점에 유사도 재계산
```

## ⚠️ 엣지케이스: 문장은 통과 but 전체는 탈락

### 발생 원리
- **문장 최대 유사도 통과** = 개별 문장은 각각 괜찮음
- **전체 유사도 탈락** = 글의 흐름·구조·논리 전개 방식이 참고 소스와 유사

> 즉, **문장은 다 바꿨는데 글의 뼈대 자체를 그대로 가져온 경우**

### 예시
```
참고 소스: 문제 정의 → 원인 분석 → 해결책 제시 → 결론
사용자 글: 문제 정의 → 원인 분석 → 해결책 제시 → 결론 (문장만 바꿈)
```

### 사용자 안내 전략

이 경우 단순히 "문장 고치세요"가 아닌, **문제의 레벨이 다르다**는 것을 명확히 안내해야 한다.

1. **구조 재편 유도** — 문단 순서 변경, 본인 관점의 단락 새로 삽입
2. **출처 명시 유도** — 구조 자체가 참고 소스에서 왔다면 인용 처리 후 의견 덧붙이기
3. **독자적 관점 추가 유도** — "이 주제에 대한 본인만의 경험이나 반론을 한 단락 추가해보세요"

### 안내 메시지 UI 예시
```
✅ 문장 유사도: 통과 (최대 31%)
❌ 전체 유사도: 미통과 (18%)

개별 문장은 괜찮지만, 글의 전체적인
흐름과 구조가 참고 자료와 유사합니다.

→ 문단 순서를 바꿔보세요
→ 본인의 의견이나 경험을 담은
   단락을 추가해보세요
→ 참고 자료를 인용 처리하는 것도
   방법입니다
```

## 💡 핵심 설계 원칙

- **1단계(문장)** 와 **2단계(전체)** 의 실패 케이스를 명확히 분리해서 안내
- 전체 유사도 체크는 문장 수정이 끝난 후 **최종 확인 단계**로 설계
- 사용자 입장에서 "문장 고치면 전체 수치도 좋아진다"는 **피드백 루프**가 직관적으로 작동하도록 구성
