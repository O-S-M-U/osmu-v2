## 1. 목적

황금 키워드로 Naver · Google 검색 결과에서 레퍼런스 블로그 글 **5개**를 수집한다.
수집된 결과는 **압축 후** Phase 1-B LLM에 전달되며, Phase 1-B가 `paragraph_blueprint`(글의 구조 초안)를 생성하는 핵심 재료가 된다.

> **수집 목적**: "이 키워드에서 현재 잘 되는 글의 구조 패턴, 단락 유형, 지배적 템플릿을 파악하기 위한 시장 조사"
> 톤(overall_tone)·템플릿 타입은 사전에 지정하지 않는다. 레퍼런스 블로그의 자연스러운 분포 자체가 데이터이기 때문.

## 2. keyword_researcher → collector 입력 페이로드

v2부터 collector는 황금 키워드 문자열만 받는 것이 아니라, keyword_researcher의 raw_signals 일부를 함께 전달받는다. fallback 분기 판단에 필요하기 때문.

```json
{
  "keyword": "직장인 야간 홈트 무릎 부담 없는 루틴",
  "score": 72,
  "is_longtail": true,
  "raw_signals": {
    "monthly_search_volume": 1200,
    "datalab_slope": 0.8
  }
}
```

| 필드 | 용도 |
|------|------|
| `monthly_search_volume` | 블로그 수 부족 시 "수요 없음(비정상)" vs "수요 있음(fallback 적용)" 구분 |
| `datalab_slope` | fallback 시 수평 분해 vs 수직 확장 전략 선택 기준 |

> keyword_researcher의 하드컷 조건(min_search_volume, slope < 0, min_blog_count)을 통과한 키워드만 collector에 도달하므로, collector 입장에서는 `monthly_search_volume ≥ min_search_volume`이고 `datalab_slope ≥ 0`임이 보장된다.

## 3. 검색엔진 배분

| 소스 | API | 수집 목표 | 특성 |
|------|-----|-----------|------|
| Naver webdoc (`webkr`) | Naver Search API | 상위 5개 요청 | 최신성 반영, 네이버 유입 기준 랭킹 |
| Google | Serper API | 상위 5개 요청 | 콘텐츠 depth · 도메인 권위도 기준 랭킹 |

- Naver webdoc을 선택한 이유: 실제 Tistory 블로그 유입 경로의 대부분이 네이버 검색. `blog` 타입은 blog.naver.com만 반환하므로 제외, 외부 블로그가 포함되는 `webkr` 사용.
- 각 소스에서 **최대 5개씩 요청(총 10개)** → 필터링 후 최종 5개 확정. 필터 탈락을 고려한 여유 수집.

## 4. 수집 파이프라인 흐름

```
[Naver webdoc API] → 최대 5개 URL
[Google Serper API] → 최대 5개 URL
        ↓
   URL 기준 중복 제거 (deduplication)
        ↓
   Pre-fetch 필터 (도메인 타입 체크)
        ↓
   Firecrawl → 본문 추출
        ↓
   Post-fetch 필터 (본문 품질 체크)
        ↓
   가중치 태깅 + source_chunk 태깅 → 최종 5개 확정
        ↓
   본문 압축 (H2 + 핵심 문장 추출)
        ↓
   5개 미달 시 → Section 9 Fallback 로직
```

## 5. 가중치 체계

Firecrawl 수집 및 필터링 통과 후, 각 블로그에 weight를 태깅한다.

| 조건 | Weight |
|------|--------|
| Naver · Google 양쪽 결과에 모두 등장 | `HIGH` |
| 단일 소스에서만 등장 | `NORMAL` |

> **근거**: 두 검색엔진 모두에서 상위에 노출되는 블로그는 최신성 + 콘텐츠 depth + 권위도를 동시에 인정받은 글. Phase 1-B LLM 프롬프트에 weight 정보를 전달하여 구조 추출 시 참고 비중을 높임.

## 6. Pre-fetch 필터 (도메인 타입 체크)

Firecrawl 호출 **전** URL만으로 판별. 크롤링 비용 낭비 방지 목적.

### 방식: Blacklist
개인 도메인 블로그(.com, .kr 등)를 whitelist로 관리하기 어렵기 때문에 **블랙리스트 방식** 채택.
아래 카테고리에 해당하는 도메인은 즉시 제거.

### 도메인 Blacklist

**쇼핑몰**
- coupang.com, smartstore.naver.com, gmarket.co.kr, 11st.co.kr, auction.co.kr, interpark.com, ohou.se

**뉴스·언론**
- news.naver.com, news.daum.net, chosun.com, joongang.co.kr / joins.com, donga.com, hani.co.kr, khan.co.kr, yna.co.kr / yonhapnews.co.kr, newsis.com, ohmynews.com

**지식백과·위키**
- namu.wiki, wikipedia.org, terms.naver.com

**정부·공공기관**

**소셜·커뮤니티**

> **운영 원칙**: Blacklist는 초기 목록으로 시작하며, 수집 결과 모니터링 후 추가/제거 필요. 별도 config 또는 DB 테이블로 관리 권장 (코드 하드코딩 지양).

## 7. Post-fetch 필터 (본문 품질 체크)

Firecrawl로 본문 추출 **후** 적용. 텍스트 기반 판별.

### 7.1 본문 길이

| 기준 | 수치 | 비고 |
|------|------|------|
| 최솟값 | **1,500자 이상** | 미만이면 내용이 얕거나 이미지 위주 글 |
| 최댓값 | **5,000자 이하** | 초과 시 목표 글(2,000~3,000자·5~7단락)과 구조 괴리 발생 |

> 이미지/텍스트 비율 별도 필터 없음. Firecrawl이 텍스트만 추출하므로 길이 필터가 이미지 과다 글을 자연스럽게 제거.

### 7.2 H2 구조

| 기준 | 수치 | 비고 |
|------|------|------|
| 최솟값 | **H2 태그 4개 이상** | 목표 단락 5~7개 기준. 인트로·아웃트로는 H2 없이 쓰는 경우가 많아 -1~2 여유 적용 |

> H2 구조가 없는 글은 Phase 1-B가 `h2_subtitle` · `core_message` 단락 패턴을 추출할 수 없음.

### 7.3 키워드 밀도 (2단계)

**1차 — 타이틀 포함 여부**

| 기준 | 처리 |
|------|------|
| 타이틀에 황금 키워드 미포함 | 즉시 제거 |

**2차 — 본문 출현 횟수**

| 기준 | 수치 | 비고 |
|------|------|------|
| 하한 | **3회 이상** | 미만이면 주제 무관 글 가능성 |
| 상한 | **15회 미만** | 이상이면 키워드 어뷰징(반복 삽입) 의심 |

### 7.4 발행 시점

| 기준 | 수치 | 비고 |
|------|------|------|
| 최신성 | **2년 이내** | 초과 시 현재 SEO 패턴 반영 불충분 |

## 8. 최종 5개 확정 로직

1. Pre-fetch + Post-fetch 필터 통과 블로그 목록 확보
2. URL 중복 제거 후 양쪽 소스 등장 여부로 weight(`HIGH` / `NORMAL`) 태깅
3. `HIGH` weight 블로그 우선 배치, 나머지 `NORMAL`로 채워 최대 5개 확정
4. 5개 미만이어도 최소 3개(`collector.min_blogs` 참조) 이상이면 다음 단계 진행

## 9. Fallback 전략 (v2 전면 재설계, v3 수평·수직 세부 보완, v4 수직 확장 상한 조정)

> **v1과의 차이**: v1은 단순히 "상위 개념 재검색 → LLM 단독"의 2단계 구조였다. v2는 keyword_researcher에서 하드컷을 통과한 키워드만 도달하므로, 블로그 수 부족의 원인을 `datalab_slope`로 구분해 전략을 분기한다.

### 9.1 전체 분기 흐름

```
필터 통과 블로그 수 ≥ 5  →  정상 진행

필터 통과 블로그 수 < 5  →  Fallback 진입

  datalab_slope > 0 (상승 중)
    →  수평 분해 전략 (Section 9.2)

  datalab_slope ≈ 0 (평탄 / 에버그린)
    →  수직 확장 전략 (Section 9.3)

  datalab_slope < 0 (하락)
    →  해당 없음. keyword_researcher 하드컷에서 이미 폐기됨.
       collector 도달 불가.
```

### 9.2 수평 분해 전략 (slope 상승 중)

**상황**: 수요는 늘고 있는데 아직 아무도 안 썼음. rising keyword.
**전략**: 키워드를 의미 단위(청크)로 분해해 청크별로 레퍼런스를 독립 수집하고, source_chunk 메타데이터를 붙여 Phase 1-B에 전달. Phase 1-B가 청크 간 공통성을 분석해 응집성 있는 blueprint를 합성.

#### 동작 방식

```
Step 1. LLM 호출 → 키워드를 의미 청크(chunk)로 분해
  입력: "직장인 야간 홈트 무릎 부담 없는 루틴"
  출력: ["직장인 야간 홈트", "무릎 부담 없는 운동 루틴"]

Step 2. 각 청크별로 독립적으로 검색 + 필터링 → 레퍼런스 수집
  (각 청크에 대해 Section 3~8과 동일한 Phase 1-A 방식 적용)
  "직장인 야간 홈트" 관련 블로그 → 수집
  "무릎 부담 없는 운동 루틴" 관련 블로그 → 수집

Step 3. 각 블로그에 source_chunk 메타데이터 태깅
  블로그 A: { source_chunk: "직장인 야간 홈트", weight: "HIGH" }
  블로그 B: { source_chunk: "무릎 부담 없는 운동 루틴", weight: "NORMAL" }
  ...

Step 4. 전체 블로그 URL 중복 제거 후 Phase 1-B에 전달
```

#### source_chunk 태깅이 필요한 이유

Phase 1-B가 청크별 공통성 기반으로 blueprint를 합성하려면, 어떤 블로그가 어느 청크에서 수집됐는지 알아야 한다. 이 정보 없이는 "청크 A와 B 모두에 등장한 주제"를 판별할 수 없고, 결과적으로 두 방향의 레퍼런스를 응집성 있게 합치는 것이 불가능해진다.

source_chunk 정보는 Phase 1-A만 알 수 있는 정보이므로, Phase 1-A가 태깅해서 전달하는 구조가 필수적이다.

> **freshness 가산점**: rising keyword는 first-mover 콘텐츠가 SEO 경쟁 우위를 가진다. Phase 1-B 프롬프트에 "이 키워드는 급상승 중인 신흥 검색어입니다. 최신성을 강조하는 구조를 우선합니다" 컨텍스트를 주입한다.

> **청크 분해를 LLM에 위임하는 이유**: 형태소 분석기(KoNLPy, Mecab 등)는 개별 형태소 단위로 쪼개므로 의미 덩어리 재조합 로직이 추가로 필요하다. v1에서는 LLM 위임이 구현 복잡도 대비 충분한 정확도를 제공한다. v2+에서 분해 품질이 병목이 될 경우 형태소 분析기로 전환을 검토한다.

### 9.3 수직 확장 전략 (slope 평탄 / 에버그린)

**상황**: 안정적으로 검색되지만 레퍼런스 블로그가 부족. 새로운 흐름이 아닌 안정된 니치.
**전략**: 원본 키워드에서 앞쪽 수식어 청크를 제거해 상위 키워드로 올라가며 재검색. **v4부터 최대 1단계로 제한.**

#### 최대 확장 단계 공식 (v4 수정)

```python
max_levels = min(1, chunk_count - 1)
```

| 청크 수 | 최대 확장 단계 | 비고 |
|---------|--------------|------|
| 1개 | **0단계** | 제거하면 검색어 자체가 사라짐 → 즉시 ⚠️ 케이스 진입 |
| 2개 이상 | **최대 1단계** | 앞 청크 1개 제거 후 재검색까지만 허용 |

> **v4 단계 상한 1로 제한한 이유**: 이 파이프라인의 핵심 목표는 레퍼런스 기반 blueprint 생성이며, 환각 없는 콘텐츠 품질이 암묵적 전제다. 수직 확장 Level 2는 앞 청크를 2개 제거하므로 "상황 맥락"(예: "야간 홈트")을 나타내는 청크까지 사라지는 경우가 발생한다. 이 경우 레퍼런스에서 해당 맥락에 대응하는 H2가 나오지 않아, Phase 1-B가 관련 단락을 레퍼런스 없이 창작해야 하고 blueprint의 일부 단락이 환각 기반이 될 수 있다. Level 1은 타겟 독자 맥락(예: "직장인")만 빠지는 수준이어서 Phase 1-B가 original_keyword를 참조해 보완 가능하며, 실제 사실·수치 주장은 Phase 2 공신력 소스로 커버된다. 맥락·프레이밍의 희석은 허용 가능한 trade-off로 판단했다.

> **단일 청크 + slope ≈ 0 케이스**: 현실적으로 극히 드문 케이스다. 단일어 키워드는 검색량이 많고 블로그 수도 많아 이 분기까지 도달하기 어렵고, 단일어인데 블로그 < 5개라면 검색량 500 미만으로 하드컷에서 이미 걸렸을 가능성이 높다. 별도의 복잡한 분기 없이 위 공식 하나로 자연스럽게 커버된다 (YAGNI).

#### 동작 방식

```
[사전 작업] LLM 호출 → 키워드를 의미 청크로 분해
  "직장인 야간 홈트 무릎 부담 없는 루틴"
  → ["직장인", "야간 홈트", "무릎 부담 없는 루틴"]  ← chunk_count = 3
  max_levels = min(1, 3-1) = 1

Level 1: 맨 앞 청크 제거 → 재검색
  "야간 홈트 무릎 부담 없는 루틴"
  → 필터링 후 min_blogs 이상 확보 시 진행
  → 미달 시 즉시 Section 9.4 (⚠️ 케이스) 진입
```

```
예시 — 청크가 2개인 경우:
  "야간 홈트 루틴" → ["야간 홈트", "루틴"]  ← chunk_count = 2
  max_levels = min(1, 2-1) = 1

Level 1: "루틴" → 재검색
Level 1 이후 부족 → 즉시 ⚠️ 케이스
```

> **앞 청크 제거 방향 고정 근거**: 한국어 롱테일 키워드에서 앞쪽 청크는 타겟 독자(직장인, 초보자 등) 또는 상황(야간, 실내 등)을 나타내는 수식어인 경우가 많다. 뒤쪽 청크가 핵심 주제(운동 루틴, 투자 방법 등)를 담고 있으므로, 앞에서 제거하면 원본 키워드의 핵심 의미를 보존하면서 상위 개념으로 올라갈 수 있다.

> **청크 분해 방식**: 수평 분해와 동일하게 LLM 위임. 수직 확장에서는 분해된 청크를 앞에서부터 제거하는 용도로만 사용한다.

#### v1 운영 후 트래킹 방침

Level 1 수직 확장으로 생성된 글의 품질과 성과를 별도 추적하여, max_levels 상향 여부를 데이터 기반으로 재검토한다.

| 트래킹 항목 | 기준 | 재검토 시점 |
|------------|------|------------|
| 수직 확장 발동 빈도 | ⚠️ 케이스 발생 비율 | 글 30개 발행 후 |
| Level 1 글의 조회수 | 정상 수집 글 대비 차이 | 글 발행 후 4주 |
| Level 1 글의 독자 반응 | 체류시간, 이탈률 | 글 발행 후 4주 |

> **max_levels 2 재도입 조건**: Level 1 글의 성과가 정상 수집 글 대비 크게 차이나지 않고, ⚠️ 케이스 비율이 높다면 max_levels를 2로 올리는 것을 검토한다. 반대로 Level 1에서도 품질 문제가 발생한다면 수직 확장 전략 자체를 재검토한다.

### 9.4 ⚠️ 케이스 — 파이프라인 중단

수직 확장 Level 1 이후에도 필터 통과 블로그가 `collector.min_blogs`(기본 3개) 미만인 경우. 수평 분해의 단일 청크 케이스(max_levels = 0)도 동일하게 처리.

```
처리:
  1. Slack 알림 전송
     제목: ⚠️ 레퍼런스 수집 실패 — 파이프라인 중단
     내용: 키워드 / 시도 이력(원본 + Level 1 결과 수) / 권고 조치

  2. 파이프라인 중단 (Phase 2 진입 없음)

  3. keyword_usages.status = failed 갱신 → in_progress 잠금 해제

권고 조치 (Slack 안내):
  - 키워드 변경 (더 넓은 키워드로 재시도 권장)
  - 수동으로 레퍼런스 확보 후 재진행
```

#### ⚠️ 케이스에서 파이프라인을 중단하는 이유

Phase 2와 Checker에 논리적 전제가 깨지기 때문이다.

```
정상 흐름의 전제:
  레퍼런스 블로그 → 구체적인 구조 + 주장 → Phase 2가 그 주장에 맞는 소스 검색
  → 소스 기반 글 작성 → Checker가 원문과 유사도 비교

⚠️ 케이스에서 발생하는 문제:
  레퍼런스 없음 → LLM이 추상적 틀 생성 → "어떤 소스를 찾아야 하는가"가 불명확
  → Phase 2 소스 탐색 목표 불명확 → Checker 비교 대상 불명확
```

v1 기준으로는 자동화를 강행하는 것보다 사용자 판단을 요청하는 것이 더 안전하다.

## 10. Phase 1-A → Phase 1-B 전달 포맷 (v3 신규)

### 10.1 포맷 개요

Phase 1-A는 수집 결과를 **압축된 형태**로 Phase 1-B에 전달한다.
수집 케이스(정상 / 수평 분해 / 수직 확장)에 따라 압축 수준이 다르다.

```json
{
  "original_keyword": "직장인 야간 홈트 무릎 부담 없는 루틴",
  "collection_type": "horizontal_decomposition",
  "chunks": ["직장인 야간 홈트", "무릎 부담 없는 운동 루틴"],
  "datalab_slope": 0.8,
  "reference_blogs": [
    {
      "url": "https://...",
      "title": "블로그 제목",
      "weight": "HIGH",
      "source_chunk": "직장인 야간 홈트",
      "compressed_content": [
        {
          "h2": "직장인 야간 운동의 장점",
          "leading_sentences": "퇴근 후 30분 홈트는 수면의 질을 높이고 스트레스를 낮춘다는 연구 결과가 있다. 특히 무릎에 부담이 적은 동작 위주로 구성하면 부상 위험도 낮출 수 있다."
        },
        {
          "h2": "추천 홈트 루틴 5가지",
          "leading_sentences": "맨몸 스쿼트, 플랭크, 브릿지 등 관절 충격이 낮은 동작을 기본으로 구성한다."
        }
      ]
    },
    {
      "url": "https://...",
      "title": "블로그 제목",
      "weight": "NORMAL",
      "source_chunk": "무릎 부담 없는 운동 루틴",
      "compressed_content": [...]
    }
  ]
}
```

### 10.2 collection_type 값

| 값 | 설명 |
|----|------|
| `normal` | 원본 키워드로 5개 정상 수집 |
| `horizontal_decomposition` | 수평 분해 후 청크별 수집 |
| `vertical_expansion_level1` | 수직 확장 1단계(앞 청크 1개 제거) 후 수집 |

> **v4 변경**: `vertical_expansion_level2`는 max_levels 1 제한으로 삭제.

### 10.3 source_chunk 필드

- `normal` 케이스: `source_chunk: null` (원본 키워드 자체이므로 구분 불필요)
- `horizontal_decomposition` 케이스: 각 블로그가 어느 청크에서 수집됐는지 표기
- `vertical_expansion_level1` 케이스: `source_chunk: null` (단일 확장 키워드로 수집되므로 구분 불필요)

## 11. 압축 전략 — Phase 1-B 전달용 본문 압축 (v3 신규)

### 11.1 압축의 목적

Phase 1-B LLM에 블로그 전문을 전달하면 5개 블로그 × 평균 3,000자 = 15,000자 이상이 된다. 토큰 비용 과다 + 핵심 신호 대비 노이즈 비율이 높아진다. 압축을 통해 Phase 1-B가 필요한 구조 신호만 받도록 설계한다.

### 11.2 압축 방식: H2 + leading_sentences

Firecrawl이 반환하는 마크다운에서 H2 섹션을 기준으로 파싱 후 각 섹션의 첫 1~3문장을 추출한다. **LLM 없이 텍스트 파싱만으로 처리 가능**하여 Phase 1-A에서 추가 LLM 호출 없이 구현된다.

```
H2 섹션 파싱 → 첫 N문장 추출 (케이스별 N 다름, 아래 참조)
```

> **설계 선택 이유**: "핵심 문장"은 LLM이 읽고 판단해야 하므로 추가 호출이 필요하지만, "첫 문장"은 규칙 기반 처리가 가능하다. 한국어 블로그 상위권 글의 경우 H2 하위 첫 문장이 해당 섹션의 방향을 소개하는 경우가 많으며, Post-fetch 필터(H2 4개 이상 조건)를 통과한 글은 최소한의 구조적 품질이 보장된다.

### 11.3 케이스별 압축 수준

| 케이스 | leading_sentences 수 | 이유 |
|--------|---------------------|------|
| `normal` | **첫 1문장** | 5개 블로그 모두 같은 키워드 → 구조 신호가 일관됨. 방향 파악에 1문장으로 충분. |
| `horizontal_decomposition` | **첫 2~3문장** (짧은 섹션은 전체) | 서로 다른 청크의 블로그를 합성해야 하므로 더 많은 컨텍스트 필요. 응집성 있는 blueprint 합성을 위해 섹션별 각도와 깊이를 파악할 수 있어야 함. |
| `vertical_expansion_level1` | **첫 1문장** | 단일 확장 키워드 검색이므로 구조 신호 일관성 유지. |

> **짧은 섹션 전체 포함 기준**: 섹션 본문이 3문장 이하인 경우 전문 포함. 어차피 토큰이 적으므로 자르지 않음.

### 11.4 압축 한계와 대응

**한계**: 첫 문장이 항상 섹션 방향을 잘 표현하지는 않는다. 특히 체험형 네이버 블로그는 "오늘 제가 해봤는데요~" 같은 맥락 도입 문장으로 시작하는 경우가 있다.

**대응**:
- Post-fetch 필터(H2 4개 이상, 1,500자 이상)가 구조 없는 글을 상당 부분 걸러낸다.
- Phase 1-B LLM이 개별 섹션 문장보다 **전체 블로그들 간의 H2 패턴 반복**에서 구조 신호를 추출한다. 5개 블로그 중 3개 이상에서 비슷한 H2가 반복된다면 첫 문장 품질과 무관하게 유의미한 구조 신호다.
- v1 운영 후 체험형 블로그 유입 비율이 높다고 판단되면 첫 문장 수를 늘리거나 LLM 요약으로 전환한다.

## 12. Phase 1-B 역할 분담 및 공통성 분석 지침 (v3 신규)

### 12.1 Phase 1-A / Phase 1-B 역할 분리 원칙

| 역할 | Phase 1-A | Phase 1-B |
|------|-----------|-----------|
| 블로그 수집 + 필터링 | ✅ | ❌ |
| 가중치(weight) 태깅 | ✅ | ❌ |
| source_chunk 태깅 | ✅ | ❌ |
| 본문 압축 (H2 + 첫 문장 추출) | ✅ (규칙 기반) | ❌ |
| 청크 간 공통성 분석 | ❌ | ✅ (LLM) |
| paragraph_blueprint 합성 | ❌ | ✅ (LLM) |
| Slack 전송 + 사용자 검토 | ❌ | ✅ |

> **설계 원칙**: Phase 1-A는 수집과 필터링, Phase 1-B는 구조 분석과 합성. 공통성 분석을 Phase 1-A에서 수행하면 Phase 1-B의 역할과 중복되고 Phase 1-A가 과중해진다. Phase 1-B의 LLM이 전체 블로그를 보고 synthesis하는 역할을 그대로 유지하면서, Phase 1-A는 source_chunk 메타데이터를 통해 "이 블로그들이 어디서 왔는지"만 알려주는 구조가 최적이다.

### 12.2 수평 분해 케이스에서의 Phase 1-B 공통성 분석

Phase 1-B는 `collection_type: "horizontal_decomposition"` 수신 시 다음 방식으로 공통성 분석 후 blueprint를 합성한다.

```
분석 1: 청크 전체에서 등장하는 H2 주제
  → 원본 키워드의 핵심 주제 (paragraph_blueprint의 주요 H2로 채택)

분석 2: 일부 청크에서만 등장하는 H2 주제
  → body_paragraph의 subtheme 후보 (중요도에 따라 포함 결정)

분석 3: 단일 청크에서만 등장하는 H2 주제
  → subkeyword 수준 (각 단락의 assigned_keywords에 반영하거나 생략)
```

**Phase 1-B 프롬프트에 포함되어야 할 지시 내용**:
1. 이 블로그들이 원본 키워드 "[original_keyword]"의 청크별 수집 결과임을 명시
2. `source_chunk` 값으로 그룹핑하여 청크별 공통 주제를 파악할 것
3. 두 청크 모두에 등장하는 주제를 글의 핵심 뼈대로 삼을 것
4. 원본 키워드의 의도를 중심으로 응집성 있는 단일 blueprint를 생성할 것
5. 청크 A와 청크 B를 각각 별개로 다루지 말고 하나의 통합된 주제로 합성할 것

### 12.3 응집성(Coherence) 확보 전략

수평 분해는 서로 다른 방향의 레퍼런스를 합쳐야 하므로 blueprint 응집성이 가장 중요한 품질 지표다.

응집성을 확보하는 세 가지 장치:
1. **source_chunk 메타데이터**: Phase 1-B가 어떤 관점의 블로그인지 파악하고 의도적으로 합성
2. **압축 수준 향상**: 수평 분해 케이스에서 2~3문장 제공으로 섹션별 각도 파악 가능
3. **명시적 합성 지시**: Phase 1-B 프롬프트에서 "두 청크를 통합한 단일 글로 작성"임을 명확히 지시

## 14. Firecrawl 호출 횟수

| 단계 | 호출 수 | 비고 |
|------|---------|------|
| Phase 1-A 정상 | 최대 10회 | 필터 후 5개 확정 목표 |
| Phase 1-A 수직 확장 Level 1 | 최대 10회 추가 | 상위 키워드로 재검색 |
| Phase 1-A 수평 분해 | 청크 수 × 최대 10회 | 청크별 독립 수집 |

> 정상 케이스 기준 월 Firecrawl 크레딧(1,000회/월 무료) 내에서 약 55~60개 article 커버 가능. fallback 발동 시 추가 소비 발생하므로 모니터링 필요. v4에서 수직 확장 Level 2 제거로 최악 케이스 Firecrawl 소비가 최대 10회 감소했다.
